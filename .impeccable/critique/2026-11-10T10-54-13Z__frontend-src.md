## 本轮修掉的（三路评审指出来的）

### P0：「没权限」被渲染成「加载失败 / 空 / 断线」

用后端真实的 403 形状（`{detail: {code, permission, message}}`）复现，四处都是假事实：
Pod 列表写「**0 个**」+ 原始 JSON + 「重试」；事件页写「**0 / 0 个事件**」；日志写「日志连接中断」；AI 面板打印原始 JSON。

「0 个 Pod」是关于集群的**假事实**——值班的人会以为集群是空的，转头去做别的检查。而「重试」在权限错误上永远不会成功。

节点页上一轮已按这个标准改过，其它页面没跟上。现在五个界面共用 `PermissionDenied.vue`（新增），`lib/apiError.ts`（新增）把后端三种 detail 形状读成 `{status, message, permission}`。

### P0：术语解释在英文界面下仍是中文

词典文案硬编码在 `lib/k8sTerms.ts` 里。界面语言跟随浏览器，英文界面点开 `FailedToRetrieveImagePullSecret` 弹出来的是中文——对一个英文界面用户完全无效，而 PRODUCT.md 承诺「英文是对等语言」。

现在：`lib/k8sTerms.ts` 只列收录清单（40 词），文案在 i18n 文件里。一个测试守着它：每个词在两种语言下都必须有解释，英文文案里不许混进中文。

### P0：AI 面板把「没权限」说成「没配置模型」

`loadProvider` 的 catch 把任何失败都当成「还没配模型」——没有 `ai.use` 的用户每次打开面板都被指向一个**他自己同样进不去**的设置页。

### P1：在跑但没就绪的容器被涂成灰

真实集群里有一个 Pod（`innies-stack-z8m-55447fff4f-tgs76`）：phase=Running，就绪探针挂了 62 天，容器 `running + ready=false`。它的容器点是**灰**的——而灰在这套颜色里意味着「还在调度或拉镜像，正常，不是信号」。一个假阴性。

`containerTone` 现在多一档琥珀（专供「在跑但不提供服务」），状态胶囊的色调跟着判定走。`podTone()` 抽成共享函数，列表和详情页用同一个——修之前它们给出两个颜色（列表琥珀、详情绿）。

### P1：`modelEndpoint` 传错了字段

它拿 provider 的**显示名**去判内外网。一个叫「本地模型」的 openai provider 会被判成「走厂商公开 API」。而且 IPv6 全判成外部（按 ':' 切分把 `::1` 切成空串），集群内短名（`http://ollama:11434`）也判成外部。

现在按 provider **类型**判定；用 `hostname` 而不是切分；加 IPv6 ULA / link-local 和单标签规则。

### P1：`extra={"model": ...}` 能改目的地

`extra` 在调用参数里最后合并，所以它能覆盖已校验的 `api_base`——把本该发到内网模型的内容发到厂商那边，而界面还显示着内网地址。`model` 现在和 `api_base` 一样是保留键。

### P1：PRODUCT.md 的一条安全断言是假的

「能把日志发给模型的人本来就有权读日志」——这在服务端并不成立：`/ai/analyze` 只要 `ai.use`，日志原文是客户端带过来的，服务端不重读也不校验 `pods.logs`。自定义角色可以配出「有 ai.use 无 pods.logs」的组合。

现在后端强制：日志分析要 `ai.use` **和** `pods.logs`。断言变成真的。

### P1：开放模式拿到的权限列表是空的

`/auth/status` 的 `permissions` 在开放模式下是空数组，而门禁把每个请求都当 `dev`（admin）放行一切。status 说「你什么权限都没有」，门禁说「你什么都有」。现在 status 按门禁用的同一个身份报权限。

### P1：弹层一打开焦点就落在链接上

点 reason 芯片 → 弹层 → 焦点自动落在「查看 Pod/xxx 详情」→ 读者按 Enter（习惯性的确认键）直接被弹走，解释一句没读到。弹层里不再放可点链接；无障碍名称带上这个词属于谁（容器名 / Pod 名 / 事件对象），同页同词的多个入口才分得开。

### P1：声明的日志体量与实发不符

面板声明整段日志的字符数（215984），实际只发最后 200 行（85863）。这个面板的主打承诺是「内容发到哪里」，读者对「我的日志发出去多少」的判断一旦失真，整句话就不可信了。现在预览和实发用同一份切片。

## 仍然开着

1. **[P1] 状态筛选与状态列排序按原始 phase** —— 289 个 Pod 里 273 个是 Running，筛「失败」得 0 条，而唯一真正坏掉的那个 Pod 就落在 Running 桶里。值班的人用「状态」找不到它。修法：筛选/排序改按判定的严重度，文案改成「需要人看一眼 / 坏了 / 正常」。**这是新功能，不是打磨。**
2. **[P2] 节点卡的「上限 110」是前端常量** —— `MAX_PODS_PER_NODE = 110` 被当集群事实断言（「超出节点上限 1 个，调度器会拒绝新 Pod」）。真集群恰好是 110，但 kubelet `--max-pods` 各集群不同（常见 30/110/250）。修法：后端补 `allocatable.pods`；拿不到就不显示上限。
3. **[P3] 事件正文纯英文无解释** —— 词典解释了名词，没解释「Readiness probe failed: HTTP probe failed with statuscode: 503」这句话，而这句话才是应用开发要读的。
4. **[P3] 仪表盘两个数字单位打架** —— 「还有 1 项需要处理」（数卡片）下面写「2 个 Warning 事件」（数事件），两个数字贴着出现像自相矛盾。
5. **[P3] 节点卡「可分配/总」零诊断价值** —— 内存 60.3Gi/60.4Gi 一眼读成「用满 99.8%」，实际是容量比。

## 设计特异性

**这个界面是为 Spotlight 写的，换个 K8s 工具不成立。** 三个证据：
1. 「判定优先于字段」落在共享函数里（`lib/container.ts` / `lib/chip.ts` / `lib/restart.ts`），三个界面共用同一个判定——任何通用 K8s Dashboard 直接显示 `phase`。
2. 术语解释挂在 reason 芯片上（`ReasonChip.vue`）而不是加个 ⓘ 图标——理由是「标题区只剩 111px 宽」，这是针对 Spotlight 自身布局做出的具体取舍。
3. AI 数据流向按 **provider 类型**而非使用者起的名字来判——实测 6 种配置，披露文案全部正确，包括把名为「本地模型」的 openai provider 正确判成「api.openai.com 看起来在你的网络之外」。

**两处本可以有产品性格却仍很通用**：节点卡是标准「资源条 + 数字」模板，完全没有 Spotlight 的判定语言；命令面板与仪表盘的「卡片 + 箭头」是通用后台骨架，产品真正的差异化只在首屏那一个 48px 数字上。

## Persona red flags

**① 凌晨三点值班的 SRE**
- 状态筛选按 phase——289 个 Pod 里「失败」是 0 条，他必须退回去读事件流。
- 节点卡给的是「可分配/总」（内存 60.3Gi/60.4Gi），一眼读成「内存用满 99.8%」，实际是容量比，零诊断价值。

**② 被塞了只读账号的应用开发**
- 事件正文是纯英文——词典解释了名词，没解释这句话，而这句话才是他要读的。
- 节点页的「上限 110」「可分配」没有任何解释入口（`?` 面板只列快捷键）。

## 总体印象与最大的机会

**总体**：扎实的运营工具，诚实的错误态，克制的视觉。错误处理和键盘效率是真做进去了——403 那套「不渲染成假事实 + 不给没意义的重试 + 精确到缺哪个权限」值得单独表扬。

**最大的机会**：把「判定」从颜色升级成**可操作的对象**。现在判定是一个颜色 + 一个理由串，读者只能「看见」它，不能「按它」找。给总览页一个「需要人看一眼的 Pod：N 个」的入口、给 Pod 列表一个按判定筛选并默认置顶的开关、让详情页与列表共用同一个判定函数——这三步做完，Spotlight 就从「把 kubectl 的字段排好版」变成「替你把该看的那几个 Pod 挑出来」。
